# 节点资源使用率和负载异常

## 覆盖告警指标

`cpu_usage_percent`、`memory_usage_percent`、`disk_usage_percent`、`load1`

## 现象和触发条件

- 节点 CPU、内存或磁盘使用率持续超过告警阈值。
- `load1` 持续高于节点 CPU 核数，或同时出现接口变慢、Pod 健康检查失败、调度延迟。
- 内存压力可能伴随 OOMKilled；磁盘压力可能伴随 Pod 驱逐、写入失败或镜像拉取失败。

## 影响范围

- 该节点上运行的 Pod 可能发生延迟、重启、限流或不可用。
- 若节点承载数据库、日志、Prometheus、Loki 等有状态组件，风险会扩大到数据写入与监控可见性。

## 所需证据

- 最近 30 到 60 分钟的 CPU、内存、磁盘、负载趋势，以及是否持续增长。
- 节点名称、CPU 核数、内存容量、运行 Pod 数和最近调度/驱逐事件。
- Top Pod/进程、磁盘目录占用、IO wait、OOM/磁盘压力事件。

## 排查步骤

1. 确认是单节点异常还是集群整体容量不足，避免把全局流量增长误判成单节点故障。
2. 查看节点和 Pod 资源排序：`kubectl top nodes`、`kubectl top pods -A --sort-by=cpu` 或 `--sort-by=memory`。
3. CPU 高时检查 `top`、`pidstat 1 5`；负载高时同时检查 `iostat -x 1 5`、`vmstat 1 5`，区分 CPU 饱和与磁盘 IO 等待。
4. 内存高时检查 OOMKilled、容器重启次数、缓存和批量任务；不要只看进程 RSS 而忽略容器限制。
5. 磁盘高时检查 `df -h`、`du -xh /var/log /var/lib/containerd /var/lib/rancher --max-depth=1`、PVC 使用和日志保留策略。

## 建议处置

- 先限制、迁移或扩容资源占用异常的工作负载，再处理长期容量问题。
- 对频繁 OOM 的服务补齐 `requests/limits`，并排查内存泄漏、缓存失控和异常重试。
- 对磁盘问题优先清理可确认无用的镜像、临时文件和已轮转日志；有状态数据应先备份和确认保留策略。
- 长期增加 HPA、资源配额、容量阈值告警和节点分布策略。

## 风险提示

- 不要在未确认目录用途时删除 `/var/lib`、PV 或数据库文件。
- 不要仅通过重启节点掩盖 CPU、内存或磁盘持续增长的根因。

## 恢复验证

- 连续观察至少两个采集周期，指标回到阈值以下且趋势稳定。
- 受影响 Pod 保持 Ready，无新增 OOM、Evicted、磁盘压力或探针失败事件。

## 升级条件

- 节点 NotReady、持续 OOM、磁盘只读、关键有状态服务无法写入，或多个节点同时资源耗尽时，升级为紧急事件。
